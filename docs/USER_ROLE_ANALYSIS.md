# Анализ текущей системы ролей пользователей

## 🎯 Цель анализа

Проверить текущее состояние данных перед внедрением ограничения:
**Один пользователь = одна роль (бригадир ИЛИ работник, но не оба)**

---

## 📊 Текущая архитектура

### Что у нас ЕСТЬ сейчас:

#### 1. **Модель User** (`schema.prisma` lines 13-61)
```prisma
model User {
  id                     String    @id @default(uuid())
  email                  String    @unique
  fullName               String
  hasCompletedOnboarding Boolean   @default(false)
  currentTeamId          String?

  // Relations
  ownedTeams         Team[]       @relation("TeamOwner")
  teamMemberships    TeamMember[]
  currentTeam        Team?        @relation("CurrentTeam")

  // ❌ НЕТ ПОЛЯ: userRole (глобальная роль)
  // ❌ НЕТ ПОЛЯ: roleSetAt (когда роль установлена)
}
```

**Проблема:** Нет глобального поля для отслеживания роли пользователя

#### 2. **Модель TeamMember** (`schema.prisma` lines 247-272)
```prisma
model TeamMember {
  id       String   @id
  teamId   String
  userId   String
  role     String   @default("member")  // 'owner' | 'member'
  position String?
  joinedAt DateTime

  @@unique([teamId, userId])  // ✅ Предотвращает дубликаты В ОДНОЙ команде
}
```

**Ограничения:**
- ✅ Unique constraint предотвращает дублирование в ОДНОЙ команде
- ❌ НЕ предотвращает членство в НЕСКОЛЬКИХ командах
- ❌ НЕ предотвращает владение командой + работу в других

#### 3. **Модель Team** (`schema.prisma` lines 158-179)
```prisma
model Team {
  id      String @id
  name    String
  ownerId String  // ✅ Указывает владельца

  owner   User         @relation("TeamOwner")
  members TeamMember[]
}
```

#### 4. **AdminRole** (`schema.prisma` lines 618-640)
```prisma
enum AdminRoleType {
  SUPER_ADMIN
  ADMIN
  MODERATOR
  SUPPORT
}

model AdminRole {
  id     String        @id
  userId String        @unique
  role   AdminRoleType
}
```

**Важно:** Это АДМИНСКИЕ роли для панели администратора, НЕ роли работник/бригадир!

## 🎯 Что мы ищем

### ✅ Идеальная ситуация:
- **0 конфликтов** - все пользователи имеют ОДНУ роль
- Пользователи делятся на:
  - **Бригадиры** (владеют командой)
  - **Работники** (члены команды)
  - **Без роли** (не создали/не присоединились к команде)

### ⚠️ Проблемная ситуация:
- **Есть конфликты** - пользователи владеют командой И являются работниками в других
- Требуется ручное разрешение перед внедрением ограничений

## 🛠️ Возможные действия

### Сценарий 1: Нет конфликтов ✅

**Можно сразу приступать к реализации:**

1. **Фаза 1: Добавить поле в БД**
   ```bash
   cd apps/api
   # Создать и применить миграцию
   npx prisma migrate dev --name add_user_role_field
   ```

2. **Фаза 2: Миграция данных**
   - Запустить скрипт, который установит:
     - `FOREMAN` для владельцев команд
     - `WORKER` для членов команд
     - `NONE` для пользователей без команд

3. **Фаза 3: Валидация в коде**
   - Обновить `teams.service.ts`:
     - `completeOnboarding()` - проверять что пользователь не WORKER
     - `joinTeamByInvite()` - проверять что пользователь не FOREMAN

4. **Фаза 4: Frontend обработка**
   - Показывать понятные ошибки пользователям

### Сценарий 2: Есть конфликты ⚠️

**Требуется ручное разрешение:**

#### Шаг 1: Идентифицировать конфликты
```sql
-- Запустить analyze-user-roles.sql
-- Посмотреть секцию "⚠️  CONFLICTS"
```

#### Шаг 2: Связаться с пользователями
Для каждого конфликтного пользователя:
1. Отправить email: "Выберите роль: Бригадир или Работник"
2. Объяснить изменения в системе
3. Предложить варианты:
   - **Остаться бригадиром** → Покинуть все команды, где работник
   - **Стать работником** → Передать владение своими командами

#### Шаг 3: Ручная корректировка данных

**Вариант A: Пользователь остается бригадиром**
```sql
-- Удалить все членства где он работник
DELETE FROM team_members
WHERE user_id = '<user_id>' AND role = 'member';
```

**Вариант B: Пользователь становится работником**
```sql
-- Вариант B1: Передать владение команды другому участнику
UPDATE teams
SET owner_id = '<new_owner_user_id>'
WHERE owner_id = '<old_owner_user_id>' AND id = '<team_id>';

-- Обновить роль в TeamMember
UPDATE team_members
SET role = 'owner'
WHERE team_id = '<team_id>' AND user_id = '<new_owner_user_id>';

UPDATE team_members
SET role = 'member'
WHERE team_id = '<team_id>' AND user_id = '<old_owner_user_id>';

-- Вариант B2: Удалить команду (если нет других участников/проектов)
DELETE FROM teams
WHERE owner_id = '<user_id>' AND id = '<team_id>';
```

#### Шаг 4: Повторно проверить
```bash
# Запустить analyze-user-roles.sql снова
# Убедиться что conflicts_count = 0
```

## 🚦 Рекомендации по порядку действий

### Минимальный путь (быстрое внедрение):

1. **Сначала проверяем данные** (этот документ)
2. **Если нет конфликтов** → Сразу добавляем валидацию в код
3. **Пропускаем поле в БД** на первом этапе (опционально)

**Преимущества:**
- ✅ Быстро (1-2 часа)
- ✅ Не требует миграции БД
- ✅ Работает через проверку relations

**Недостатки:**
- ❌ Медленнее запросы (JOIN к Team и TeamMember)
- ❌ Нет single source of truth

### Полный путь (рекомендуется):

1. **Проверяем данные** (этот документ)
2. **Разрешаем конфликты** (если есть)
3. **Добавляем поле `userRole`** в User модель
4. **Мигрируем существующие данные**
5. **Добавляем валидацию в код**
6. **Обновляем frontend**

**Преимущества:**
- ✅ Быстрые запросы (без JOIN)
- ✅ Single source of truth
- ✅ Легко добавлять features (фильтры по роли, статистика)

**Недостатки:**
- ❌ Требует больше времени (1-2 дня)
- ❌ Нужна миграция данных

## 📞 Что делать, если застряли

### Проблема: SQL запрос не работает
**Решение:** Проверьте подключение к БД, правильность названий таблиц

### Проблема: Много конфликтных пользователей
**Решение:**
1. Отправить массовую рассылку всем конфликтным пользователям
2. Дать 30 дней на выбор роли
3. После дедлайна - авто-разрешение по приоритету (владелец > работник)

### Проблема: Пользователь хочет быть и тем, и тем
**Решение:** Объяснить бизнес-логику:
- Бригадир управляет командой, работники выполняют работу
- Разделение ответственности улучшает систему
- Если нужны обе роли - создать два аккаунта (не рекомендуется)
