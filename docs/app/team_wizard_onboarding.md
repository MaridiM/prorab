# Wizard команды vs обязательный онбординг

## 1. Что есть что

* **Wizard создания команды**

  * Цель: быстро создать НОВУЮ бригаду/команду.
  * Точка входа: по кнопке «Создать бригаду» внутри уже работающего аккаунта.
  * Использование: многоразовое (2-я, 3-я, 4-я бригада и т.д.).

* **Обязательный онбординг после первого входа**

  * Цель: настроить стартовое рабочее пространство, чтобы не было «пустого» приложения.
  * Шаги: назвать первую бригаду → выбрать/загрузить логотип → создать первый объект.
  * Точка входа: только при самом первом логине нового пользователя/организации.
  * Без прохождения онбординга пользователь не попадает в основной интерфейс.

## 2. Приоритет и связь задач

### Приоритет

1. **Сначала – обязательный онбординг**

   * Это критический UX: первый опыт пользователя.
   * После онбординга в системе гарантированно есть:

     * хотя бы одна бригада;
     * её визуальная идентичность (логотип);
     * минимум один объект для работы.
2. **Потом – общий wizard создания команды**

   * Используется, когда продукт уже живёт, и пользователь хочет добавить ещё одну бригаду.

### Это одна задача или две?

* Логически — **две разные задачи**:

  * Онбординг = сценарий первого запуска продукта.
  * Wizard = обычный рабочий инструмент CRUD для сущности «бригада».
* Технически их можно связать:

  * Онбординг просто **переиспользует ядро wizard’а** для шага «создание первой бригады».
  * Разница — в обёртке и контексте (обязательность, наличие прогресса, блокировка выхода).

## 3. Ответ на вопрос "должен ли wizard быть обязательным онбордингом?"

* **Нет, wizard создания команды сам по себе не обязан быть онбордингом.**
* **Правильная модель:**

  * Онбординг = отдельный поток, который внутри содержит:

    1. Шаг создания первой бригады (на базе того же wizard’а, но в упрощённом виде).
    2. Шаг логотипа.
    3. Шаг первого объекта.
  * После онбординга тот же wizard доступен в интерфейсе как отдельная функция: «Создать новую бригаду».

## 4. Итоговое решение (обновлено)

* Приоритизировать **обязательный онбординг после первого входа**.
* Реализовать **ядро wizard’а команды** так, чтобы его можно было:

  * использовать внутри онбординга (для первой бригады);
  * вызывать отдельно позже для создания новых бригад.

Таким образом, это **две связанные, но разные задачи**: онбординг (первичный запуск) и wizard (рабочий инструмент).

## 5. Дополнительно: кнопка «Пропустить / Меня пригласили» и сценарий приглашения

### 5.1. Кнопка на первом экране онбординга

В онбординге должны присутствовать две логические опции:

* **«Пропустить»** — может быть доступна только для тестового режима или администраторов.
* **«Меня пригласили»** — основной путь для сотрудников, которых добавил бригадир.

### 5.2. Что происходит при выборе «Меня пригласили»

Если пользователь выбирает этот вариант, он должен перейти в поток **активации приглашения**.

#### Как бригадир приглашает участника

1. Бригадир открывает страницу своей бригады.
2. Нажимает «Пригласить участника».
3. Заполняет форму:

   * Email сотрудника
   * Роль (работник / мастер / прораб)
4. После отправки система:

   * создаёт **token приглашения**,
   * отправляет письмо со ссылкой вида: `https://…/invite?token=XYZ`.

#### Что видит приглашённый участник

1. Открывает ссылку и попадает на страницу активации.
2. Проходит короткий мастер:

   * подтверждение email,
   * создание пароля,
   * (опционально) имя и аватар.
3. После активации автоматически попадает в интерфейс своей бригады — **онбординг не нужен**.

### Почему это важно

* Работник не должен создавать собственную бригаду.
* Не должен проходить логотип и первый объект.
* Поток становится быстрым, гладким и логичным.

## 6. Итоговое объединённое решение

1. **Онбординг** — обязательный поток для новых самостоятельных пользователей.
2. **Wizard создания бригады** — рабочий инструмент внутри системы.
3. Онбординг может использовать ядро wizard’а для шага создания первой бригады.
4. На первом экране онбординга обязательно должны быть кнопки:

   * «Пропустить» (по необходимости),
   * **«Меня пригласили» → переход в поток активации приглашения**.

## 7. Готовый ответ на продуктовый вопрос

**Вопрос:**

> Приоритет между wizard создания команды и обязательным онбордингом. Это одна и та же задача или две разные? Должен ли wizard команды быть обязательным онбордингом для нового пользователя?

**Ответ (концепция, которую мы предлагаем):**

Нет, wizard создания команды сам по себе не обязан быть онбордингом.

Мы разделяем два сценария:

1. **Обязательный онбординг после первого входа** — это отдельный поток, который запускается только один раз для нового самостоятельного пользователя/организации и содержит три шага:

   * Шаг 1: создание первой бригады (на базе того же wizard’а, но в упрощённом виде: только название + базовые параметры).
   * Шаг 2: выбор или загрузка логотипа бригады.
   * Шаг 3: создание первого объекта (чтобы пользователь не попадал в «пустое» приложение).

   На первом экране онбординга показываем две ключевые опции:

   * **«Начать настройку»** — идём по 3‑шаговому онбордингу.
   * **«Меня пригласили»** — переход в поток активации приглашения (для работников, которых уже добавил бригадир).

2. **Wizard создания команды** — это отдельный, многоразовый инструмент внутри уже работающего аккаунта. После онбординга пользователь видит в интерфейсе кнопку «Создать новую бригаду», которая открывает тот же wizard, но уже **в полноценном режиме** (все поля, участники, роли и т.п.).

Таким образом, это **две разные задачи по смыслу**, но технически они используют общее ядро:

* онбординг переиспользует упрощённый wizard для создания **первой** бригады;
* далее тот же wizard доступен как обычная функция для создания **дополнительных** бригад.

---

### Дополнительно: как бригадир приглашает участников

Для сценария «Меня пригласили» предлагаем такой механизм:

1. **Генерация кода приглашения бригадиром**

   * Бригадир открывает страницу своей бригады и нажимает «Пригласить участника».
   * Система генерирует **6‑значный код приглашения** (например: `483921`), привязанный к конкретной бригаде и сроку действия (например, 24–72 часа).
   * Код можно скопировать и отправить любым способом: в Telegram, WhatsApp, SMS и т.д.
   * Дополнительно можно сделать интеграцию с Telegram‑ботом, который по команде `/invite` пришлёт бригадиру новый код.

2. **Активация приглашения приглашённым пользователем**

   * На первом экране онбординга пользователь выбирает «Меня пригласили».
   * Открывается форма с простым полем: **«Введите 6‑значный код бригады»**.
   * После ввода и валидации кода система:

     * связывает пользователя с нужной бригадой,
     * предлагает задать пароль и имя,
     * сразу переводит в интерфейс бригады **без прохождения онбординга по созданию своей команды, логотипа и объекта**.

3. **Альтернативы и возможные расширения**

   * Приглашение по email/ссылке (magic‑link), которое ведёт на ту же форму активации и автоматически подставляет код.
   * QR‑код приглашения (для оффлайн‑команд), который сканируется и подставляет код автоматически.

Такой подход даёт чёткое разделение ролей:

* **Самостоятельные пользователи** проходят обязательный онбординг и создают свою первую бригаду.
* **Приглашённые работники** идут по короткому сценарию «Меня пригласили», вводят 6‑значный код из Telegram (или переходят по ссылке) и сразу попадают в уже существующую бригаду, не создавая свою.

## 8. Пропуск шагов онбординга

**Вопрос:**

> Можно ли пропускать шаги онбординга? Например:
> – пропустить загрузку логотипа,
> – пропустить создание демо-объекта,
> или все 3 шага обязательны?

### ✔️ Ответ: часть шагов может быть пропускаемой, часть — обязательная

Онбординг должен быть максимально коротким, простым и не перегруженным. Но при этом он должен привести пользователя в рабочее состояние. Поэтому шаги делим на два типа:

---

### 🟥 1. Обязательные шаги (нельзя пропустить)

Эти шаги критически важны, чтобы пользователь не попал в «пустое» приложение:

1. **Название первой бригады**

   * Без этого невозможно создать рабочую структуру.

2. **Создание первого объекта (ввод названия)**

   * Должно обеспечивать наличие хотя бы одного объекта сразу.
   * Пользователь вводит ТОЛЬКО название.
   * Всё остальное заполняется автоматически демо-данными.

Эти шаги должны быть обязательными, иначе нарушится логика UX и onboarding flow.

---

### 🟩 2. Пропускаемые шаги (можно пропустить)

Некоторые элементы не являются критичными и могут быть установлены позже:

#### ✔️ Шаг “Логотип” — МОЖНО пропустить

Если пользователь нажимает «Пропустить», система:

* ставит **заглушку‑иконку** (один из стандартных вариантов),
* позволяет изменить логотип позже в настройках бригады.

Причины, почему пропуск логотипа допустим:

* часть пользователей не имеет готового логотипа;
* дисциплина «скину потом» не блокирует работу;
* не стоит заставлять пользователя искать фото или файл на телефоне.

#### ✔️ Демо‑объект — создаётся автоматически после шага названия

Пользователь вводит **только название объекта**, остальные данные добавляются автоматически.

Пропустить полностью — НЕТ (иначе пустой интерфейс),
но делать ручной ввод — тоже не нужно.

Поэтому это «полуобязательный» шаг.

---

### 🟦 3. Почему нельзя разрешать пропуск ВСЕХ шагов

Если пустить пользователя дальше без бригады и объекта:

* интерфейс будет пустым;
* нечему обучать (нет объектов → нет задач → нет расходов → нет фото);
* onboarding loses its purpose.

Онбординг должен гарантировать минимально рабочую структуру:

* 1 бригада,
* логотип (или заглушка),
* 1 объект с демо‑данными.

---

## 📌 Итоговое решение для спеки

**Пропускаемые шаги:**

* Логотип (подставляется заглушка)

**Обязательные шаги:**

* Создание первой бригады (название)
* Создание первого объекта (название, затем авто‑создание демо‑данных)

**Нельзя пропускать весь онбординг полностью.**

Если хочешь — могу также:

## 9. Backend: готовность и модель Team

**Вопрос:**

> Нужно ли мне создать backend API (Team модель, мутации, upload) или это уже готово? Если создавать — какие поля должны быть в Team модели?

### 9.1. Готовность backend’а

С точки зрения спецификации логично считать, что под onboarding и wizard бригады потребуется **отдельная поддержка на backend’е**:

1. **Модель Team (или Brigade)** в базе данных.
2. **GraphQL/REST-методы** для:

   * создания первой бригады в онбординге;
   * создания дополнительных бригад через wizard;
   * обновления названия, логотипа и настроек;
   * получения списка бригад пользователя.
3. **Механизм загрузки логотипа**:

   * либо прямой upload (multipart) до сервера;
   * либо выдача pre-signed URL (S3/аналог) и сохранение `logoUrl`.

Если этого ещё нет в проекте — это отдельный backend-эпик под фичу «Бригады/команды + онбординг».

---

### 9.2. Рекомендуемая модель Team

Базовый состав полей для модели `Team` (или `Brigade`), ориентируясь на спецификацию и UX:

**Идентификация и связи:**

* `id` — уникальный идентификатор.
* `ownerId` — владелец/бригадир (пользователь, создавший бригаду).

**Основные данные:**

* `name` — название бригады.
* `slug` (опционально) — человекочитаемый код/алиас для URL.
* `logoUrl` — ссылка на логотип (или `null`, если используется заглушка).
* `color` (опционально) — основной цвет бригады (для UI).

**Тариф и статус:**

* `plan` — тарифный план (enum: `FREE`, `START`, `PRO`, …).
* `status` — статус бригады (например, `ACTIVE`, `ARCHIVED`).

**Настройки/контекст:**

* `currency` — валюта по умолчанию (для расходов/отчётов).
* `locale` — локаль (формат дат/языка интерфейса).
* `measurementUnits` — единицы измерения (м², пог. м и т.п., если нужно).
* `settings` (json) — дополнительные опции (видимость, уведомления и др.).

**Служебные поля:**

* `createdAt`
* `updatedAt`

Связанные сущности (не обязательно полями, но через отношения):

* **Участники** — связь `TeamMember`/`UserOnTeam` (роль, права и т.п.).
* **Объекты** — `Project`/`Site`/`Object`, связанные с конкретной бригадой.
* **Приглашения** — `TeamInvite`/`InviteCode` для сценария «Меня пригласили».

---

### 9.3. Модель Invite/InviteCode (для сценария «Меня пригласили»)

Отдельная модель для кодов приглашений, чтобы реализовать сценарий активации:

* `id`
* `teamId` — к какой бригаде относится приглашение.
* `code` — 6-значный код.
* `role` — роль для подключаемого участника (worker/master/foreman).
* `expiresAt` — срок действия кода.
* `usedAt` (nullable) — когда код был использован.
* `createdAt`

### 9.4. Готовый ответ на продуктовый вопрос

**Ответ:**

Backend под эту часть функционала нужно явно поддержать.

Для онбординга и wizard’а создания бригады нам требуется:

1. **Модель Team/Brigade** c полями:

   * идентификаторы: `id`, `ownerId`;
   * основные: `name`, `logoUrl`, (опционально) `slug`, `color`;
   * тариф и статус: `plan`, `status`;
   * настройки: `currency`, `locale`, `measurementUnits`/`settings` (json);
   * служебные: `createdAt`, `updatedAt`.

2. **API-слой**:

   * мутация для создания первой бригады в онбординге;
   * мутация для создания дополнительных бригад через wizard;
   * мутация для обновления названия/логотипа/настроек;
   * запросы для получения списка бригад и одной бригады по `id`.

3. **Механизм загрузки логотипа**:

   * либо upload на сервер с последующей записью `logoUrl`,
   * либо pre-signed URL (облачное хранилище), куда грузит фронт, а backend хранит только ссылку.

4. **Модель Invite/InviteCode** для сценария «Меня пригласили» — генерация 6-значного кода, привязка к бригаде, срок действия и одноразовое использование.

Такой набор покрывает все сценарии онбординга, повторного создания бригад и приглашения участников, о которых мы договорились выше.

## 10. Модель участника: Member / TeamMember

Чтобы закрыть сценарии ролей и прав в бригаде, добавим отдельную сущность **участника команды**.

### 10.1. Зачем нужна отдельная модель

`Team` описывает саму бригаду (как организацию).
`User` описывает учётную запись человека.

Связка «какой пользователь в какой бригаде, в какой роли и с какими правами» — это отдельная сущность:

> **TeamMember** (или `UserOnTeam` / `Member`)

Так мы получаем:

* одного пользователя, который может состоять в нескольких бригадах;
* разные роли и права в разных бригадах;
* управление статусом участника (активен, приглашён, удалён и т.д.).

### 10.2. Рекомендуемая структура TeamMember

Базовый набор полей:

* `id` — уникальный идентификатор записи.
* `teamId` — к какой бригаде относится участник.
* `userId` — какой пользователь.
* `role` — роль участника в бригаде (enum, например: `OWNER`, `ADMIN`, `FOREMAN`, `WORKER`, `ACCOUNTANT` и т.п.).
* `status` — статус участника:

  * `INVITED` — приглашён, но ещё не активировал аккаунт;
  * `ACTIVE` — активно работает в бригаде;
  * `SUSPENDED` — временно отключён;
  * `REMOVED` — удалён.
* `permissions` (опционально, json/bitmask) — тонкая настройка прав поверх роли (можно добавить позже).
* `joinedAt` — когда пользователь присоединился к бригаде.
* `leftAt` (nullable) — когда был удалён/ушёл.
* `createdAt`, `updatedAt` — служебные поля.

### 10.3. Связь с приглашениями (Invite/InviteCode)

Поток выглядит так:

1. Бригадир генерирует **InviteCode** (6-значный код) для конкретной бригады и роли.
2. Приглашённый пользователь вводит код или переходит по ссылке.
3. Backend:

   * находит актуальное приглашение,
   * создаёт/подтверждает `User`,
   * создаёт запись `TeamMember` со статусом `ACTIVE` и ролью из приглашения,
   * помечает приглашение как `usedAt = now`.

Таким образом:

* **Team** отвечает за саму бригаду;
* **TeamMember** — за связь пользователя с бригадой, роль и статус;
* **InviteCode** — за процесс подключения новых участников через сценарий «Меня пригласили».

### 10.4. Краткий ответ для спеки

При моделировании команд/бригад рекомендуем ввести отдельную сущность `TeamMember` (или `UserOnTeam`), которая связывает `User` и `Team` и хранит роль, статус и даты присоединения. Это позволит одному пользователю работать сразу в нескольких бригадах с разными ролями и облегчит реализацию сценариев приглашения участников по 6‑значному коду или ссылке.
