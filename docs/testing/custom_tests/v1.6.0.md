### Test 3.5: Downgrade Protection - Backend

**Objective:** Verify downgrade is blocked when usage exceeds new plan limits.

**Prerequisites:**
- User on FOREMAN plan (10 projects, 15 members, 50 GB)
- User has:
  - 8 active projects
  - 12 members
  - 35 GB storage used

**Steps:**
1. User attempts to downgrade to LITE plan (3 projects, 5 members, 10 GB)
2. Call `changePlan` mutation with LITE plan slug
3. Backend should validate and reject

**Expected Results:**
- ✅ `ForbiddenException` thrown
- ✅ Error response:
  ```json
  {
    "message": "Невозможно понизить план. Превышены лимиты нового плана.",
    "extensions": {
      "code": "DOWNGRADE_LIMIT_EXCEEDED",
      "exceeds": [
        "Проекты: 8 > 3",
        "Участники: 12 > 5",
        "Хранилище: 35.00 ГБ > 10 ГБ"
      ]
    }
  }
  ```
- ✅ Subscription plan NOT changed
- ✅ User remains on FOREMAN

**Backend Method:** `SubscriptionsService.changePlan()`

**Validation Logic:**
```typescript
// 1. Get current and new plan details
// 2. Check if isDowngrade (sortOrder comparison)
// 3. If downgrade:
//    - Get usage stats (projects, members, storage)
//    - Compare against new plan limits
//    - Build exceeds array
//    - Throw ForbiddenException if any exceed
```

### Test 3.6: Downgrade Protection - Frontend Modal

**Objective:** Verify downgrade error modal displays correctly.

**Prerequisites:**
- User attempts downgrade that would exceed limits
- Backend returns DOWNGRADE_LIMIT_EXCEEDED error

**Steps:**
1. User clicks "Change Plan" to downgrade
2. Backend rejects with error
3. Frontend catches error and displays modal
4. Review modal content

**Expected Results:**
- ✅ `DowngradeErrorModal` opens
- ✅ Title: "Невозможно понизить план"
- ✅ Description shows new plan name
- ✅ Alert box lists all exceeded limits:
  - "Проекты: 8 > 3"
  - "Участники: 12 > 5"
  - "Хранилище: 35.00 ГБ > 10 ГБ"
- ✅ Recommendations section shows:
  - Archive/delete unused projects
  - Remove inactive team members
  - Clear old files/photos
- ✅ Buttons: "Закрыть" and "Посмотреть другие планы"
- ✅ Clicking "Посмотреть другие планы" → `/settings?tab=billing`

**Component:** `DowngradeErrorModal`

**Usage Example:**
```typescript
const [downgradError, setDowngradeError] = useState<DowngradeError | null>(null);

const handleChangePlan = async (newPlanSlug: string) => {
  try {
    await changePlan({ variables: { input: { newPlanSlug } } });
  } catch (error) {
    if (error.extensions?.code === 'DOWNGRADE_LIMIT_EXCEEDED') {
      setDowngradeError({
        message: error.message,
        code: error.extensions.code,
        exceeds: error.extensions.exceeds,
      });
    }
  }
};

<DowngradeErrorModal
  isOpen={!!downgradError}
  onClose={() => setDowngradeError(null)}
  error={downgradError}
  newPlanName="LITE"
/>
```

## 🐛 Known Issues & Edge Cases

### Issue 1: Widget Dismissal Persistence
**Status:** By Design
**Description:** UpgradeWidget dismissal only persists in localStorage, resets on browser clear.
**Impact:** Low - users will see widget again after clearing browser data.
**Solution:** Could store dismissal in database if needed.

### Issue 2: Real-time Limit Updates
**Status:** To Be Implemented
**Description:** Limits update on page refresh, not in real-time.
**Impact:** Low - most limit checks happen on mutations anyway.
**Solution:** Could add subscriptions for real-time updates.
